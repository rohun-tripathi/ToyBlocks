Recorded Dataset Fields#

Datasets are stored in LeRobot v3 format. Execution records one row per engine tick (4 physics steps, 0.04 s), so episodes are written at 25 fps. All pose and motion quantities are expressed in the robot base frame (local frame) unless stated otherwise. The local frame is defined by the robot’s base link position and orientation at the time of recording, with poses transformed via world_to_local.

Quaternions use [qw, qx, qy, qz] (scalar-first) convention. Euler angles use intrinsic ZYX (roll, pitch, yaw) in radians.

Camera Observations#

Execution records no cameras by default, so none of these columns exist in an executed dataset unless it was run with --record-videos. They normally come from re-rendering.

Field

Shape

Dtype

Description

observation.images.<cam>

(H, W, 3)

video (uint8 RGB)

RGB image from the named camera, encoded as AV1 video at dataset fps. The resolution comes from the scene’s camera config: 360×640 (H×W) for the shipped scenes’ cameras. Camera names carry a camera: prefix, e.g. observation.images.camera:front_camera.

observation.depth.<cam>

(H, W, 1) or (H, W, 3)

video (uint16)

Depth map in millimetres (0–4095), divide by 1000 for metres. Stored as 12-bit gray12le (1 channel, the default) or as rg8 (the same value packed into 3-channel 8-bit RGB: R = low byte, G = high byte). Read video.depth_encoding (gray12le_mm or rg8_mm) in the feature’s info in meta/info.json before decoding. Source is Isaac Lab distance_to_image_plane.

observation.images.<cam>_<variant>

(224, 224, 3)

video (uint8 RGB)

Optional RGB sidecar from --extra_rgb, e.g. _224.

observation.depth.<cam>_<variant>

varies

video

Optional depth sidecar from --extra_depth, e.g. _g12_224, _rg8_224 or _rg8_55_224. Has its own resolution, channel count and video.depth_max_mm; read them from meta/info.json. rg8_55_224, the pipeline default, packs depth as (R << 5) | G and saturates at 1023 mm, unlike rg8’s R + (G << 8), yet both record video.depth_encoding: rg8_mm; tell them apart by the key suffix or by video.depth_max_mm (1023 vs 4095).

observation.camera_pose.<cam>

(7,)

float32

Camera extrinsic pose [x, y, z, qw, qx, qy, qz] in the robot base frame.

observation.camera_intrinsics.<cam>

(9,)

float32

Flattened 3×3 camera intrinsic matrix [fx, s, cx, 0, fy, cy, 0, 0, 1] (row-major).

Tactile cameras (if present) follow the same observation.images.<cam> convention but may have different resolution.

Actions#

All action fields represent per-timestep commands sent to or derived from the controller.

Row t holds the observation of state t together with the action that drives state t to state t+1. The last row of an episode is the terminal state: its action columns are zero and action.is_valid is False. Train on action.is_valid rather than testing for zeros, since an all-zero action.joint_target is itself a reachable pose.

Other Recording Paths#

Datasets recorded outside vecgen, by evaluation or the RecordEpisode wrapper (src/toyblocks/wrappers/record_episode.py), can carry extra columns:

  • action.policy: the raw policy action, sized to the env’s action space.

  • action.hl_input_prompt, action.hl_model_output, action.hl_prev_action (strings) and action.hl_done (bool), when a high-level model chooses the actions.

  • observation.state.object_mass and observation.state.table_mass: live PhysX masses, NaN when the query fails.

  • observation.images.<cam>_hl_overlay: the camera stream with the high-level prediction drawn on it.

USD Assets and Provenance#

USD assets are not saved in the dataset. Object meshes (e.g. letter-shaped toy blocks) and robot models are loaded at simulation time from the assets/ directory (gitignored, distributed separately) via OBJECT_ASSET_DIR and ROBOT_ASSET_DIR. The dataset only contains rendered camera images, numeric state, and actions — not the raw 3D geometry.

However, the dataset does include provenance metadata under meta/ that records what was used to generate the data:

File

Description

meta/recording_config.json

Recording parameters: gripper binarize threshold, gripper type (robotiq), open/close commands, joint velocity limits, record_videos, and robot_link_pose_frame.

meta/provenance.json

Git commit/remote, the recording_provenance dict used at creation, and SHA-256 checksums of every file copied into meta/extra/. In a merged dataset it is one aggregate: the git metadata of the merge, merged_from_n_datasets, and one sources[] entry per source dataset (its path, problem_name, extra_dir and files).

meta/extra/

Copies of source files, only for the paths the recorder was given: domain.pddl, <problem>.pddl, and, from the env directory, block_config.json, init.py and the <id>.json instance files. A merged dataset keeps one domain.pddl (from the first source that has it) at meta/extra/domain.pddl, and each source’s other copies under meta/extra/<problem>/.

meta/render_params.json

Re-rendered datasets only, before merge: how each split was rendered and every per-episode randomization value; see Re-rendering. Merge does not carry it into the merged meta/.

Vecgen passes only instance_json_ids and generator: vecgen as provenance, so for datasets from execution meta/extra/ is empty and provenance.json holds the git metadata alone. To reproduce such a dataset’s simulation environment, you need:

  1. The ToyBlocks repository at the recorded git commit (from meta/provenance.json).

  2. The assets/ directory with the matching USD meshes and robot models.

  3. The PDDL problem and the env package it was generated from. The problem is named by the source_problem column; the dataset does not carry copies.
