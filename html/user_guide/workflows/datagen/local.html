Running the pipeline on this machine#

scripts/datagen/run_datagen_pipeline.py runs the whole data generation pipeline on the machine you launch it on: PDDL problems, env packages, executed episodes, re-rendered videos and a merged LeRobot dataset, all on local disk and local GPUs. The same command works on a single-GPU workstation and on a multi-GPU node; the pipeline spreads problems over every GPU it can see.

This page covers what is specific to running it: choosing GPUs and concurrency, where outputs and logs go, re-rendering, resuming, and checking the result. For the stage-by-stage reference, see Automatic Data Generation.

Stage

How it runs

task-gen

one subprocess, on the CPU

env

one process per problem, across the GPU slots (skipped with --vecgen-problems-per-env > 1, the default)

execution

one process per problem or problem group, across the GPU slots

rerender

one render per problem, in the same GPU-slot pool (--rerender) or inside each execution job (--rerender-local)

merge

one subprocess, on the CPU

annotate

one subprocess, on the CPU

The pipeline needs no network access once the assets are installed. Run it from the root of the checkout: the stage scripts are called by relative path (scripts/...), and the pipeline runs git rev-parse HEAD to pin the commit into the run config for reproducibility.

Before you start#

Follow the installation instructions: with the virtual environment active, install the datagen (vecgen) extra and fetch the assets:

uv pip install -e ".[dev,isaac,torch-cu128,vecgen]"

get-toyblocks-assets --asset-manifest asset_manifest.json

Re-rendering with the default flags draws HDRI backdrops from polyhaven (installed with the base assets) and the separately licensed Laval indoor set; see HDRI backdrops.

Re-rendering needs real disk. A run of a few problems at --rerender-n 2 writes several GB of video; check free space before a long run rather than discovering it mid-encode.

A complete run#

This generates 4 stacking problems, executes 16 episodes each, re-renders them, and merges the result into one LeRobot dataset under ./outputs:

python scripts/datagen/run_datagen_pipeline.py --rerender-local \
    --experiment-id my_run --output-root outputs \
    --task-gen-script scripts/task_gen/stack_three.py --task-gen-count 4 \
    --env-per-problem 16 --num-envs 16 --exec-num-envs 16 \
    --vecgen-problems-per-env 1

The merged dataset is annotated at the end, since the re-render supplies the camera data that annotation projects goals into. Drop --rerender-local to stop after execution and merge the raw parquet (state and actions, no video); the pipeline then logs a warning and skips annotation, which needs video (--rerender, --rerender-local or --vecgen-record-videos).

Without any flags beyond --experiment-id, the pipeline uses the settings the RI stack-3 training set was generated with: 1000 stack_three.py --train problems, randomized scenes, 32 reset states per problem, 8 problems per vecgen env package at 128 envs.

Each stage also runs on its own; see task generation, env generation, execution, re-rendering, merge and annotate.

Choosing GPUs and how many problems run at once#

Flag

Default

Meaning

--local-gpus ID [ID ...]

every GPU visible to the process

Which GPU ids the stages may use.

--local-gpu-workers N

1

Concurrent problems per GPU. 1 is a strict no-op.

The pipeline builds one slot per GPU per worker, so len(gpus) * workers problems run at once. Each slot owns one CUDA_VISIBLE_DEVICES value, so every job sees a single GPU; a stage scales out by spreading problems over more slots, never by giving one problem several GPUs. Listing a GPU id twice in --local-gpus gives it two slots, like --local-gpu-workers 2 does.

GPU discovery honours an existing CUDA_VISIBLE_DEVICES; failing that it asks nvidia-smi, and if that is unavailable it runs one problem at a time on the default GPU.

A failing problem does not abort the stage. The stage keeps going and reports the failure count at the end, and the next stage works with the problems that succeeded.

Measured on one RTX 5090 (32,607 MiB) at --rerender-local-num-envs 8:

Two concurrent processes fit comfortably on a 32 GiB card and one does not saturate it, so --local-gpu-workers 2 is usually free throughput. Read “Host RAM and disk, not VRAM, are the limits” under Things that will bite you first.

Logs#

With a single slot, every job’s output is streamed to your console. With more than one slot, each problem’s output goes to its own log file instead, since concurrent Isaac Sim logs are unreadable interleaved:

<base>/local_logs/env/<slug>.log
<base>/local_logs/execution/<slug>.log
<base>/local_logs/rerender/<slug>.log

The pipeline logs the directory when it does this, and a FAILED <stage>: <slug> (see ...) line names the log of each problem that failed. [sched] <stage> start|end <slug> slot=... t=... lines record when each job ran, which is how per-stage timings are measured. The pipeline’s own log goes to the console only; pipe it through tee if you want to keep it.

The merged dataset gets a copy of the run config and a plot of its first episode, episode_0.png.

Re-rendering locally#

Execution records state and actions only — vecgen spawns no cameras by default. The videos come from the re-render stage, which replays the recorded states with no physics and renders them under the domain randomization in a flags YAML. See Re-rendering for what that stage does and every flag it takes, and the YAML reference for how to write the randomization.

Two flags turn the stage on, and they pick how it is scheduled against the executions. Both produce the same pixels — the rerender.py argv, the staged source layout and the per-problem output directory name (which is the domain-randomization seed salt) are identical, so a problem draws the same randomization either way. The choice is about throughput and observability, not about how the dataset looks.

--rerender (pipelined)

--rerender-local (coupled)

where the render runs

its own item in the shared GPU-slot pool

inside the execution job’s own shell chain, vecgen && rerender

when it becomes eligible

the moment that problem’s execution finalizes

immediately, holding the slot its execution just used

can overlap the next execution

yes, whenever a slot is free

no — one job, one slot

exec vs render timing

separate items, separate logs, separate [sched] lines

not separable (one process span)

a render failure

its own item with its own log

indistinguishable from an execution failure in the job’s exit code

They are alternatives; passing both is refused. Neither can be combined with --vecgen-record-videos: recording in-physics video and then overwriting it pays the slow physics-render cost for frames nothing reads.

The render defaults are the RI training set’s: the flags YAML src/blocksuite/domain_randomization/flags/rerender_flags_allrand_texcache_glyphs_trainsplit_symmetric.yaml (--rerender-flags), one copy per episode (--rerender-n 1), the 224 RGB and rg8_55_224 depth sidecars, left_camera skipped and failure episodes skipped. The flags YAML must be readable on this machine; the pipeline checks it before starting.

Which mode to use#

Measured over 4 problems, 2 reps, execution + re-render window only (BENCHMARK_local.md):

1 slot

2 slots (--local-gpu-workers 2)

coupled (--rerender-local)

921 s

667 s

pipelined (--rerender)

906 s

733 s

For throughput, use --rerender-local --local-gpu-workers 2 — 28% faster than a single coupled slot, and it needs none of the scheduler. Pipelining costs nothing at one slot but loses about 10% at two, because its render-first ordering pairs render against render (two GPU-saturating processes), whereas the coupled chains naturally pair one problem’s execution against another’s render.

Use the pipelined mode when you want separable exec/render timings and logs, failure isolation between the two, a first finished problem early rather than at the end of a chain, or bounded un-rendered disk.

Options that matter on one machine#

Flag

Default

Meaning

--rerender-local-num-envs

8

Envs per render wave, in both modes. A floor, not a preference: the re-render spawns env i at block-size slot i % profiles, so a value below --num-scene-profiles leaves the high slots without an env and every problem is skipped. The pipeline refuses that pairing up front. 8 keeps the encoder’s RSS survivable beside Isaac.

--rerender-local-stall-timeout

3600

SIGKILL the render if it prints nothing for this many seconds.

--rerender-local-fail-on-video-defects

off

Fail a problem whose encoder could not publish every video. Off by default because a failed problem re-renders whole; scripts/rerender/fast_patch.py fills video holes afterwards.

--rerender-n, --render-non-randomized, --rerender-skip-cameras and --rerender-extra are described in Re-rendering, along with what --rerender-n and --render-non-randomized actually multiply and how to check that they did.

What counts as “rendered”#

Once the rerender stage is marked complete, merge reads only rerender/out/job_*. A problem that executed but was never re-rendered would simply vanish from the merged dataset. To stop that being silent, a post-stage sweep classifies every problem on disk into three states:

State

Meaning

Retried?

RENDER_SHIPPED

finalized under blocks_success and merge can read it (info.json present)

no — it is done

RENDER_UNRENDERABLE

finalized, but it can never ship: it declared itself empty, recorded zero episodes, or finalized with only a blocks_failure split

no — permanent, and failing on it would wedge every later run

RENDER_ABSENT

not finalized, or finalized without a readable dataset

yes — the run exits non-zero and a later run or --resume finishes it

Two of these are worth understanding. completed: true in render_params.json means terminal, not has data. And a problem whose episodes all failed finalizes with blocks_failure alone, so no blocks_success is ever created; re-running cannot change that, because the source has no successful episodes.

Both modes report from this sweep, never from the job list, so it also covers problems the execution loop skipped, runs with --skip-execution, resumed runs where the execution stage was disabled, and preemption shards (problem_x__s001). The merge gate asks merge’s own discovery what it would ship, rather than globbing problem_* — the execution stage creates each problem’s output directory before running it, so a crashed execution leaves an empty directory behind for good. Pass --merge-allow-missing-problems to merge what rendered and drop the rest.

Flags that do not do what their name suggests#

Flag

What actually happens

--num-reset-states

Dead. The env stage passes --num_reset_states <--env-per-problem>, and the multi-problem path passes --env-per-problem too. Use --env-per-problem (default 32) to control reset states.

--env-per-problem

Despite the name, this is the number of reset states per problem, not a number of environments. The environment count is --num-envs (sampling) or --exec-num-envs (execution).

--num-scene-profiles

The count is baked into the env package at codegen time, so changing it does nothing for a problem whose package already exists — see below.

--seed

With --vecgen-problems-per-env 1, it does not reach env generation: the env stage is hard-wired to ENV_GEN_SEED = 0, so re-running with a different --seed regenerates identical reset states and --seed affects execution only. With multi-problem packages (the default), the package for the group starting at problem g is sampled with --seed + g, so --seed changes the reset states too.

--vecgen-episodes

Only used with --vecgen-problems-per-env 1. A multi-problem job runs --env-per-problem episodes per problem in its group.

The env-count constraint is “a multiple of the profile count, or strictly smaller than it” — --num-envs 4 against 8 profiles is legal and spawns only the low slots. It is not “must be a multiple”.

With --vecgen-problems-per-env > 1 the env stage is switched off entirely — the execution jobs build the multi-problem packages themselves with scripts/vecgen/make_superset_env.py.

Render arguments the pipeline pins for you#

The pipeline builds its own rerender.py command line, and three of its arguments differ from rerender.py’s own defaults. They are worth knowing if you are comparing a pipeline render against one you ran by hand:

Argument

Pipeline passes

rerender.py default

--env_spacing

60

unset (scene default 5.0)

--camera_base

scene

data

--rtx_warmup_frames

16

1

--num_envs comes from --rerender-local-num-envs. Anything you pass through --rerender-extra is appended last and therefore wins over all of these.

Env generation also skips any problem whose reset_states.pkl already exists, and a multi-problem job skips building a package whose problems.json exists. That is what makes re-running cheap — and what makes a stale env package silently survive a parameter change. Delete the problem’s env directory, or use a fresh --experiment-id, when you change env-stage parameters. This applies to --num-scene-profiles in particular: the profile count is a property of the package, not of the run, so re-running an existing experiment with a new count keeps the old bake.

Resuming#

--resume continues a previous run of the same --experiment-id: stages already marked complete in <base>/.pipeline_state/ are skipped, and the first unfinished stage is rerun from scratch, deleting its outputs first. It is a no-op if the experiment directory does not exist.

What that deletes matters for long runs. If the execution stage was interrupted, --resume deletes execution/ and rerender/, including the problems that had already finished. The rerender stage is the exception: it deletes nothing, and rerender.py --resume renders only the problems not yet completed. A run interrupted after its executions finalized therefore resumes straight into rerender instead of silently merging raw parquet.

A stage is marked complete when it finishes, even if some of its problems failed, so --resume does not retry failed problems. To keep finished problems and run only the missing or failed ones, rerun the same command without --resume and with --skip-task-gen (otherwise task generation writes a fresh batch of problems next to the old ones): env generation skips problems whose reset_states.pkl exists, and execution skips problems whose .execution_complete marker exists.

Verify the output#

Metadata cannot see a broken render. A dataset can carry completed: true and still contain videos no decoder will open — a host-RAM OOM mid-encode produces moov atom not found mp4s behind a perfectly healthy-looking marker. Validate the pixels after any run above one worker:

python scripts/rerender/validate_dataset_videos.py <base>/rerender/out/job_local

To confirm that --rerender-n genuinely multiplied, count episodes, frames and distinct video files — never bytes. Merge hardlinks videos into the merged tree, so du of the merged directory is meaningless, and different random draws compress differently. See Re-rendering.

Things that will bite you#

Re-rendering segfaults at startup on some GPU/driver combinations#

On an RTX 5090 with driver 595.99.02, every local render died about 7 s into Isaac startup with a SIGSEGV in librtx.scenedb.plugin.so, while env generation and execution ran fine on the same GPU. This is an Isaac Sim 5.1 RTX-renderer problem, not ToyBlocks. Check your machine with:

python -c "from isaaclab.app import AppLauncher; AppLauncher(headless=True, enable_cameras=True)"

If that crashes, the machine cannot render: run the pipeline without a rerender flag and re-render the executed episodes on a machine that can (see Re-rendering). The same crash affects --vecgen-record-videos and eval video capture. Kit logs are under .venv/lib/python3.11/site-packages/isaacsim/kit/logs/Kit/Isaac-Sim/5.1/.

Harmless PhysX errors#

Some otherwise clean runs print PxDirectGPUAPI::getRigidDynamicData(): not allowed while simulation is running. The episodes still succeed; ignore it.

Isaac hangs after it finishes#

rerender.py prints all jobs done and then hangs in Isaac teardown — observed holding a GPU for 53 minutes after finalizing all 16 episodes. Every pipeline render therefore runs through scripts/rerender/run_local_render.py, which watches for the marker and kills the process group after a grace period. Never key completion on an exit code here; key it on the log.

Host RAM and disk, not VRAM, are the limits#

VRAM is not the binding constraint when raising --local-gpu-workers — host RAM is, and a host-RAM OOM mid-encode corrupts videos behind a completed: true marker. Raise the worker count only if you validate the output afterwards.

Concurrent slots share Isaac’s caches#

The pipeline sets KIT_CACHE_ROOT, KIT_LOG_DIR and OMNI_USER_CONFIG_DIR per slot, but the installed Isaac Sim does not read any of them. Concurrent slots still share ~/.cache/ov, ~/.local/share/ov and ~/.nvidia-omniverse. The one per-slot variable that does take effect is TMP3_ENCODER_THREADS, which stops N processes each sizing an encode pool from the whole CPU set.

--camera_base data does nothing here#

It tells the renderer to base each static camera on the pose the dataset records. The execution stage records no camera pose at all — vecgen is parquet-only, so there is never a recorded pose to base on. rerender.py detects this, warns loudly, and falls back to --camera_base scene; the pipeline passes scene explicitly and drops a data arriving through --rerender-extra. Same outcome, said at argv-build time instead of minutes into Kit startup.

--rerender-extra needs the = form#

Argparse reads a space-separated value starting with - as an option of its own:

--rerender-extra="--extra_rgb 224 --extra_depth g12_224 --depth_gop 1000"   # works
--rerender-extra "--skip_failure_episodes"                                  # rejected

It is appended last, so it beats the pipeline’s own --depth_gop, --dr_seeding, --camera_base and --env_spacing, and the default sidecars. --output, --envs_dir, --episodes_file, --episode_offset and --max_episodes are dropped with a warning — they break the pipeline’s accounting rather than the render.
