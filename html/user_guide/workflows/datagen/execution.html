Stage 3: Execution (vecgen)#

Execution is where the demonstrations are actually produced. Given an env package and its reset states, the robot has to work out how to reach the goal from each starting scene, carry out that plan in simulation, and have every step recorded as training data.

scripts/vecgen/run.py does all of this in one Isaac process. It loads the env package, plans every environment with the FF symbolic planner, runs the planned skills as batched cuRobo motion plans, checks each skill’s effect against the live simulation, and records a LeRobot v3 dataset. Planning happens inside the same process, per environment, so there are no pre-computed plan pickles and no TAMP checkout to manage.

Where it fits#

  • Input: an env package with reset_states.pkl, from stage 2, plus the PDDL problem and domain.

  • Output: a LeRobot dataset split into successful and failed episodes, read by re-rendering or directly by merge.

This stage always runs. By default it records state and actions only; the camera videos come from re-rendering, as explained in What a recorded episode contains.

Correct by construction#

The point of this stage is that every episode it labels successful really is a success. That guarantee comes from a plan, act and verify loop:

  1. FF plans each environment from its own symbolic state.

  2. After every skill, that skill’s verify() runs against the live simulation.

  3. If the check fails, the environment is restored to its pre-skill snapshot (sim state, held block and cuRobo attachment), the retried frames are dropped from the dataset, and the skill is retried with freshly sampled parameters.

  4. After --max-attempts failed attempts, FF re-plans from the live state, at most twice.

  5. If that also fails, the episode ends as a failure.

  6. At the end of the program the PDDL goal facts are checked again, so an episode is labelled successful only if the goal actually holds.

Failed episodes go to a separate blocks_failure split rather than being mixed in or discarded, so you can study them later.

Running it#

To run the flip env package from stage 2 and record 32 episodes with 16 environments in parallel:

python scripts/vecgen/run.py \
    --env-path outputs/flip \
    --pddl src/blocksuite/tamp/blocks/problems/flip.pddl \
    --domain src/blocksuite/tamp/blocks/domain.pddl \
    --num-envs 16 --episodes 32 \
    --record datasets/flip --mark-complete --headless

The two counts mean different things:

  • --num-envs is concurrency: how many environments run side by side on the GPU.

  • --episodes is the total number of episodes to finish, successes and failures together.

When an environment finishes an episode, it is immediately reset onto the next reset state of its own scene-profile slot and starts planning again. Environments keep recycling like this until the episode target is met.

--record names the output directory, and creates blocks_success/ and blocks_failure/ underneath it. --mark-complete writes a summary and a completion marker when the run finishes cleanly; see Output.

Environment variables#

A few recording settings have no flag at all and are read from environment variables. The pipeline’s stages inherit your shell’s environment, so export them before launching, or set them on the run.py command line:

TMP3_RECORDER_INFLIGHT_GB=8 python scripts/datagen/run_datagen_pipeline.py --experiment-id ...

Variable

Default

Effect

TMP3_RECORDER_INFLIGHT_GB

4 GiB or a quarter of RAM, whichever is smaller

How much un-encoded video may be queued before recording pauses the simulation. Only matters with --record-videos.

TMP3_ENCODER_THREADS

all available cores

The size of the video encoder’s thread pool. When more than one GPU slot runs at a time, the pipeline sets it to the cores divided by the number of slots, unless you set it yourself.

The arm dynamics and the motion profile are flags, not environment variables; see Flags. The flip and rotate skill tuning and the cuRobo collision settings are fixed in code.

Output#

Everything is written under the --record directory:

Path

Contents

<--record>/blocks_success/

Episodes whose PDDL goal held at the end.

<--record>/blocks_failure/

Every episode the engine ended as a failure, with the reason.

<--record>/results.json

Only with --mark-complete: per-episode records, failure reasons and wall time.

<--record>/.execution_complete

Only with --mark-complete. The pipeline uses it to decide whether to resume or skip this problem.

<--record>__s001/, __s002/

Shards written when a preempted run resumes; see Common pitfalls.

To check a run, look for RUN_OK and the RESULT ... line in the log, and read the failure reasons in results.json.

What a recorded episode contains#

By default this stage records no cameras at all. The env is built with cameras=False, so the camera prims are never spawned, and the recorder leaves out every video feature. There is no observation.images.* and no observation.depth.*, and also no observation.camera_pose.* or observation.camera_intrinsics.* columns. The output is Parquet only.

This keeps execution fast; the pixels normally come from the rerender stage instead. It is also why the re-render’s --camera_base data cannot work on a dataset this stage recorded: there is no recorded camera pose to start from, so the pipeline renders with --camera_base scene.

Each row is one engine tick, written at 25 fps. A row holds is_first and is_last; observation.state and the per-joint position, velocity, acceleration and effort vectors; the gripper, ee_position and wrench; the 13-DoF stiffness, damping, effort-limit, velocity-limit and torque vectors; observation.state.object_pose.<name> for every rigid object; observation.state.contact_force.<sensor> per contact sensor; robot.poses.<link> for every robot body; the scene parameters; the provenance columns (scene_id, robot_id, source_problem, instance_id); pddl_goal; the symbolic state; the action block, including action.joint_position and action.joint_target; and the high- and low-level action labels.

Every column is described in Dataset fields.

If you do want video from this stage, --record-videos is not enough on its own. Isaac also has to be told to render, so pass --enable_cameras as well.

Common pitfalls#

A mistyped flag is ignored, or quietly does something else#

run.py uses parse_known_args, which it needs for Isaac’s AppLauncher, so a flag it does not define is dropped without a word.

There is a subtlety. The parser leaves allow_abbrev at its default, so any unique prefix of a real flag is accepted as that flag. --record-video is therefore not ignored: it turns video recording on. --num-env 4 and --pool-s 8 work too, while an ambiguous prefix such as --pool is an error. A typo is either silently ignored or silently honoured, depending on whether it happens to be a prefix, so double-check flag names against the table above.

Some limits cannot be changed from the command line#

Three limits live in EngineConfig and have no CLI flag: max_replans = 2, max_episode_ticks = 6000 (the episode is ended with reason "episode tick limit"), and done_hold_ticks = 25 (the hold recorded after the last skill).

A run aborts because a scene profile has no reset state#

Reset states are bound to scene profiles, not to environments. Environment i spawns in slot i % MAX_NON_SIM_STATE_RANDOMIZATIONS and may only run reset states whose block sizes and friction match that slot. If a spawned slot has no compatible reset state, the run aborts with a RuntimeError.

Without --reset-states-once, a profile’s reset states cycle, so asking for more episodes than there are reset states replays some of them.

--mark-complete does not notice lost videos#

It writes .execution_complete without consulting the video encoder’s defect counter, so a --record-videos run that lost videos can still be marked complete. Only the rerender tooling checks video_defects().

Episodes go missing at merge time because of the directory name#

Merge only picks up base_dir/problem_*/blocks_success, and the source_problem column is taken from the deepest path component starting with problem_, falling back to the directory’s own name. For a nested path like .../problem_grp_flip/problem_0007 that is problem_0007, not the group. Name the --record directory accordingly.

An empty directory still counts as shard 0, which is why the pipeline creates the problem directory before launching. run.py never scans for shards itself, so a retried attempt leaves the previous partial shard on disk.

The process seems to hang after finishing#

After the run, run.py arms a 15 s timer and calls os._exit(rc), because simulation_app.close() can hang when headless. So the process may take a while to go away. Poll the log for RUN_OK / RESULT ... rather than waiting for the process to exit.

results.json counts more episodes than the dataset#

If FF fails, or the plan uses an action vecgen has no skill for, the episode is counted in results.json as a failure with reason "no program", but it produces no dataset episode, because start_episode was never called. Episodes with zero frames are also skipped at save time. So the two counts can legitimately differ.
