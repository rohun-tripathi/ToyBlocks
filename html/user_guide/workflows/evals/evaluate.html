evaluate.py Reference#

scripts/evaluate.py is the eval worker: launch_eval.py runs one per eval GPU, each pulling episodes from the episode queue. You can also run it by hand, for example to debug one worker against a policy server you started yourself. This page covers its action sources, how to run it against a server, the observation transforms, its flags and its outputs. For the full pipeline, see Policy Evaluation.

evaluate.py parses the Args dataclass in src/blocksuite/eval/args.py with tyro, and hands it to blocksuite.eval.run_eval.evaluate. Args also inherits the Isaac launcher options of BaseArgs (--device (default cuda:0), --headless (on for eval), --enable_cameras, --kit_args, --rendering_mode) and the nested env-config overrides --env-cfg.<field> (for example --env-cfg.robot-id droid_franka). Flags accept - or _ between words, and boolean flags are turned off with --no-<flag>. Isaac starts before the arguments are parsed, so even --help launches it.

Before the run starts, evaluate.py also:

  • adds --enable_cameras when --obs_mode contains rgb;

  • snaps --num_envs to a value the task accepts (reconcile_num_envs_with_task), since autogen block tasks bake a fixed number of cube-size slots;

  • with --dataset_path, defaults the eval robot_id and scene_preset_id to the dataset’s recorded provenance, warning on a mismatching override and failing when the provenance is missing and no override was given (see Dataset scene provenance).

Action sources#

evaluate.py picks where actions come from based on its flags:

Source

Selected by

Use for

Remote policy server

--policy_host (+ --policy_port, default 8000)

Evaluating the served ManiFlow / Molmo2 policies, or any model behind the BasePolicy interface.

Random actions

--random_actions

Sanity checks: uniform in [-1, 1].

Zero actions

none of the above

Sanity checks of task spawning and metrics.

Dataset replay

--replay with --queue_url, --dataset_path and --num_envs 1

Playing back each queued episode’s recorded actions and reporting how far the simulation diverges from the recording.

--random_actions raises when combined with --policy_host, and --replay raises when combined with either.

Random and zero actions#

python scripts/evaluate.py --task Blocksuite-Lift-v0 \
    --random_actions --num_envs 4 --num_eval_steps 200

--random_actions samples every action component uniformly from [-1, 1]; with no action source at all, every step gets a zero action. Both are handy for confirming that a task spawns correctly and that recording and metrics work before plugging in a policy.

Dataset replay#

Replay is easiest through the launcher, which also starts the queue:

python scripts/launch_eval.py --replay \
    --dataset-path data/datasets/my_dataset --episode-indices "0"

See Dataset Replay for how replay works, its metrics and its requirements.

Running against a policy server by hand#

Running the server and the eval worker in two terminals is the easiest way to debug either side with breakpoints.

1. Start a policy server (terminal 1), serve_maniflow_policy. --hl oracle serves the ManiFlow LL alone (the client supplies the high-level commands); --hl model serves Molmo2 + ManiFlow:

export H_VLA_PATH=$PWD/maniflow-tb PYTHONPATH=$PYTHONPATH:$PWD/maniflow-tb

# ManiFlow, with the high-level oracle on the client
python -m blocksuite.serving.serve_maniflow_policy --port 8000 --hl oracle \
    --checkpoint data/checkpoints/my_maniflow_run/checkpoints/steps_400000_model.safetensors \
    --config data/checkpoints/my_maniflow_run/config.yaml \
    --train_config maniflow-tb/examples/Franka/train_maniflow_multimodal.yaml

# Molmo2 high level + ManiFlow low level
python -m blocksuite.serving.serve_maniflow_policy --port 8000 --hl model \
    --checkpoint data/checkpoints/my_maniflow_run/checkpoints/steps_400000_model.safetensors \
    --hl_checkpoint data/checkpoints/my_molmo2_run \
    --config data/checkpoints/my_maniflow_run/config.yaml \
    --train_config maniflow-tb/examples/Franka/train_maniflow_multimodal.yaml

2. Run the eval worker (terminal 2). Prompts and per-episode setups come from the episode queue (--queue_url, started with python scripts/serve_episode_queue.py --dataset-path <root> --port 8001) and the dataset (--dataset_path), and the task must already be generated (see Policy Evaluation):

python scripts/evaluate.py \
    --task <task-slug>-v0 \
    --policy_host localhost --policy_port 8000 \
    --queue_url http://localhost:8001/next --dataset_path data/datasets/my_dataset \
    --control_mode arm_joint_gripper_binary \
    --obs_mode rgb+state --obs_transform maniflow_blocks_table \
    --action_horizon 25 --sync_action_chunks --num_envs 2 \
    --use_oracle --save_lerobot

Drop --use_oracle against the --hl model server; launch_eval.py passes --hl_from_model there instead.

Split-terminal scripts. scripts/eval/serve_local_server.sh (terminal 1) and scripts/eval/serve_local_client.sh (terminal 2) wrap these steps and match launch_eval.py’s ManiFlow and Molmo2 inputs. Both run in the foreground with plain python, so a breakpoint() in the server, the eval client or an obs transform is hit interactively (launch_eval.py backgrounds everything with redirected output). Activate the venv first:

# Terminal 1: policy server (POLICY_NAME=maniflow serves --hl oracle)
MODEL_PATH=data/checkpoints/my_maniflow_run/checkpoints/steps_400000_model.safetensors \
HL_MODEL_PATH=data/checkpoints/my_molmo2_run \
    bash scripts/eval/serve_local_server.sh

# Terminal 2: task generation + episode queue + evaluate.py
DATASET_PATH=data/datasets/my_dataset EPISODE_INDICES=0,3 \
    bash scripts/eval/serve_local_client.sh

Their configuration (policy, checkpoints, dataset, ports, num_envs cap) lives once in scripts/eval/_common.sh, sourced by both; override any variable inline. POLICY_NAME defaults to molmo2_maniflow (--hl model). MODEL_PATH (and HL_MODEL_PATH for molmo2_maniflow) and DATASET_PATH (or PDDL_PROBLEM_FILE, to generate the task from a PDDL problem instead) have no defaults, and the scripts exit with a message when one is missing. The client waits for the server’s port, then either runs one batched pass sized to the queue (PER_EPISODE=0, the default with --hl oracle) or one task generation, queue and single-environment evaluate.py per episode (PER_EPISODE=1, the default with --hl model). Results go under runs/ (OUT_PATH). Note that both scripts first kill your own stale servers, queues and evaluate.py processes.

Key flags:

  • --obs_transform: how observations are converted for the policy (see Observation transforms).

  • --unbatched: call the server once per environment instead of once per step with a batch of all environments, for servers that add their own batch dimension. launch_eval.py always runs batched.

  • --action_horizon N: the server returns chunks of actions and one is applied per step; --sync_action_chunks puts all environments on the same chunk boundary so the server is queried once per chunk (the pipeline always sets it).

  • --save_lerobot: record the rollouts as a LeRobot dataset, including the raw policy actions.

A policy that returns 9-dim actions (7 arm joints, gripper, pd_mode) switches the controller gains through its trailing pd_mode channel; no flag is needed. The channel drives the same PD-mode controller as replay, and is stripped before env.step. Depth images are added to the observations automatically when the served checkpoint expects them.

Any model can be served by implementing the small BasePolicy interface; see Setting up a new policy server.

Observation transforms#

Registered in src/blocksuite/serving/obs_transforms/__init__.py and selected with --obs_transform (default none, which sends the raw observations):

Name

Use for

maniflow

ManiFlow Franka policies.

maniflow_blocks_table

Same as maniflow, mapping the blocks-table cameras (front_camera / gripper_camera) onto the policy’s front_rgb / gripper_rgb. The default of launch_eval.py.

The ManiFlow agent_pos width is the served checkpoint’s, not a flag: the server advertises state_dim in its metadata, and the client builds the state from STATE_DIM_LAYOUTS (obs_transforms/maniflow.py): 8 (7 arm + 1 gripper), 9 (+ pd_mode) or 19 (+ 7 joint velocities and 3 EE xyz). Without metadata it defaults to 19; any other width raises.

These flags apply to the ManiFlow transforms only, and raise with any other transform:

Flag

Default

Description

--center_crop_ratio

none

After the resize to 224, centre-crop RGB, depth and target_heatmap to int(224 * ratio) and resize back (inference counterpart of random_crop_ratio, e.g. 0.95).

--depth_aug

none

Live depth augmentation before the policy sees depth; ejbl matches HVLA’s augment_depth.

--enable_crop

off

Build target_front_crop_rgb on the client from the native front camera and target pixels. Needs a checkpoint with use_target_front_crop >= 0.

To add a transform, subclass BaseObsTransform, override transform (and optionally action_postprocess), and register it in _lazy_registry.

Metrics#

--track_metrics, --track_joint_metrics and --track_ee_metrics are on by default; --save_step_metrics (per-step CSVs) is off. Contact-force tracking is an env-config option (--env-cfg.track-collisions). See Metrics for every metric and output format.

Replay#

--replay and --replay_clip_stats; see Dataset Replay.

TAMPER#

--tamper_output_dir captures the terminal sim state of every unsuccessful episode as a vecgen env package, so new expert demonstrations can be planned from those states. --tamper_capture_successes, --tamper_max_states and --tamper_source_env_path refine it. See TAMPER.

W&B#

--wandb mirrors throughput, per-episode metrics and videos to a W&B run (needs WANDB_API_KEY). --wandb_project (default blocksuite-eval), --wandb_entity, --wandb_group (none by default), --wandb_name, --wandb_job_type, --wandb_tags and --wandb_log_interval_seconds configure it. Pipeline runs leave it off and merge all workers into one run instead (see launch_eval.py outputs).

Policy-input verification (--save_diagnostic_plots) answers “is the policy being fed what it was trained on?” rather than “did it succeed”. For every environment at the first reset, then for the followed video environment at each episode start, it renders two PNGs into policy_input_debug/ from the live obs transform’s own output:

  • per depth camera: the raw sim depth, the depth the model receives (after process_depth, optional depth augmentation, point-map Z masking and the centre crop), the episode’s recorded frame-0 depth, their signed difference and both histograms. A constant offset is a calibration or units mismatch; structured residue is a scene mismatch.

  • the state panel (*_state.png): each agent_pos dimension against the [q01, q99] band the server normalizes it into. Dimensions drawn in red are outside the training band.

The panels are capability-gated: a run with no policy server, no ManiFlow transform, or a server that advertises no normalization bands prints why it skipped them and carries on. On its first inference the server also logs, per depth camera, how much of the back-projected point map its clamp saturates (ptmap saturation ...); high saturation means the scene sits outside the checkpoint’s point-map bounds even when both depth columns look healthy. The server-side traces (ll_policy_input_trace/, and hl_policy_input_trace/ for Molmo2) are rendered inside the policy server just before the model call, one PNG per handover, so they show the tensors the model actually receives.
