launch_eval.py Reference#

scripts/launch_eval.py is the recommended entry point for evaluation. It does not run anything itself: it turns its flags into the environment variables of scripts/eval/run_eval_pipeline.sh, the one pipeline that starts the policy server, generates the gym task from the dataset, serves the episode queue, runs the eval workers and merges the results (see Policy Evaluation). This page lists every flag it accepts.

Everything runs as subprocesses on this machine, from your working tree as it is:

  • GPU layout. GPU 0 runs the policy server and GPUs 1..N run the N eval workers (GPUs 0..N-1 under --replay, which has no server). With fewer GPUs than that, the workers share the visible GPUs round-robin; on a one-GPU workstation the single worker shares GPU 0 with the policy server.

  • --dry-run prints the env VAR=... bash scripts/eval/run_eval_pipeline.sh invocation instead of running it (--output writes it to a file), so you can inspect, edit and rerun it by hand.

  • Submodules. Policy evals need the maniflow-tb (package hvla) and molmo2 (package olmo) submodules, installed by the maniflow extra (see Installation and setup). The pipeline refuses to start if either is missing, or if maniflow-tb is not checked out at the commit this checkout pins; fix it with git submodule update --init maniflow-tb molmo2. --replay needs neither.

The gym task is generated from --dataset-path: its slug is the dataset directory’s basename with - replaced by _ (gym id <slug>-v0), unless --task-name overrides it.

Flags are spelled with hyphens (a few also accept an underscore alias), and on/off flags marked “on” below are turned off with --no-<flag>. Only the flags on this page reach evaluate.py; there is no pass-through for other evaluate.py flags.

The episode queue#

Every eval episode starts from a recorded episode of --dataset-path. The pipeline starts scripts/serve_episode_queue.py, a small HTTP server (port 8001) that loads one setup per dataset episode at startup and hands them out one at a time. All eval workers pull from this one queue, so each episode runs exactly once across all GPUs:

LeRobot dataset ──> serve_episode_queue.py ──GET /next──> evaluate.py (worker 1)
                         │                  ──GET /next──> evaluate.py (worker N)
                         └──GET /size──> run_eval_pipeline.sh (sizing)

What a setup holds. load_setups in utils/episode_dataset.py builds one setup per episode from the LeRobot parquet columns. Among other things:

  • the episode’s pddl_goal, and its hl_prompt when one is recorded;

  • the robot’s starting joint and gripper positions, and every block’s pose;

  • the table height or pose, the camera intrinsics, the block size (cube_scale) and friction;

  • the expert episode’s length and videos, and the frame it starts from (init_frame_index).

A trimmed example:

{
  "episode_id": "ep_000001",
  "pddl_goal": "(and (on block_b block_a))",
  "robot_joint_positions": [0.0, -0.785, 0.0, -2.356, 0.0, 1.571, 0.785],
  "robot_gripper_position": 0.04,
  "objects": {
    "block_a": {"position": [0.5, 0.0, 0.05], "quaternion": [1.0, 0.0, 0.0, 0.0]}
  },
  "table_height_delta": 0.0,
  "expert_episode_length": 310
}

Whenever environments reset, the worker fetches the next setup for each of them (EpisodeQueueClient.fetch_reset_states) and writes it into the simulation (apply_setup). Joints and objects a setup does not list keep their reset values, but apply_setup raises instead of guessing on a setup/scene mismatch: an object the scene does not spawn, a missing gripper joint, or a table with neither a recorded pose nor a height delta. One step later, the worker checks that the simulation state matches the setup; with --queue-log-level DEBUG the client also logs every fetched setup and every joint and object write.

Prompt resolution. The language instruction sent to the policy (and logged as the episode’s prompt) is the setup’s hl_prompt (parquet goal.hl_prompt) when present; otherwise the setup’s pddl_goal is turned into English by pddl_goal_to_prompt (for example (and (on block_b block_a)) becomes “put the B block on the A block”). Each environment gets its own episode’s prompt. For molmo2_maniflow the same string is the Molmo2 task; --hl-prompt "stack 2 blocks" forces one fixed goal for the whole run.

Which episodes are queued.

  • --episode-indices (with --allow-duplicate-episodes to repeat an episode) selects the episodes, as 0,3,5,10-19 or @file.txt (a file of the same entries). The pipeline passes the same selection to task generation and to the queue.

  • --init-after-hl-action moves each episode’s start to just after a given high-level action. The robot and block poses, the expert first frames and the --expert-timeout-scale budget then come from the cut (the remaining expert length).

  • --queue-limit caps how many are queued.

The queue hands out the longest expert demonstrations first, so the episodes likely to run longest start early and the last stragglers are short ones.

Sizing from the queue. Before starting the workers, the pipeline reads GET /size:

  • Each worker gets min(ceil(queue size / --num-eval-gpus), --num-envs) parallel environments, so a small queue does not spawn idle environments.

  • With --expert-timeout-scale, episode_length_s is raised to cover that multiple of the queue’s longest expert demonstration (expert_seconds_max), so each episode’s own budget is the timeout that binds.

Block-size slots. Block size cannot change after spawn, so when the dataset records a cube_scale per episode, the generated task spawns one slot per distinct size and the queue serves each environment only episodes of its slot’s size. A worker spreads its environments over the slots in proportion to each slot’s queued workload, which it reads from /size (slot_counts, slot_expert_frames). Every fetch also sends the task’s slot ordering, and the queue fails if it differs from its own. That catches a task generated from different --episode-indices than the queue was started with. The queue also refuses to start if only some of the episodes record a cube_scale.

When the queue drains. An environment whose fetch comes back empty keeps stepping on the task’s default randomization. These “phantom” episodes are never scored or recorded, but they still cost policy inference and physics. A worker stops once all of its environments have drained, and the pipeline prints the queue’s final status at the end.

Endpoints:

  • GET /next: {"setup": ...}, or null once drained. With block-size slots, add ?slot=<i>&slot_scales=<s0,s1,...>.

  • GET /size: remaining, total, expert_seconds_max, slot_counts and slot_expert_frames. The queue fails at startup if the dataset’s meta/info.json has no fps, since expert_seconds_max needs it.

  • GET /healthz: {"ok": true}.

Dataset requirements#

A run consumes one artifact, the LeRobot dataset at --dataset-path. It is the source of truth for:

  1. The per-episode setups above. Each needs at least observation.state.joint_position and pddl_goal; the other columns (gripper position, block poses, table pose, friction, intrinsics, …) are used when present.

  2. The gym task. generate_task_from_dataset.py reads the block list from the observation.state.object_pose.<name> columns and every distinct pddl_goal (quantified, typed goals such as (exists (?b1 ?b2 - block_red) ...) are grounded against the scene’s blocks). Block names resolve to assets by name: a glyph name (block_a .. block_z, block_1 .. block_9) spawns that glyph block from --usd-library, a name in USD_OVERRIDES (in tamp/blocks/template/codegen.py) its USD, and anything else a cuboid coloured by the colour word in its name.

  3. The scene. See Dataset scene provenance.

If the dataset has observation.images.* videos, the queue also resolves each episode’s expert clips, which the W&B episodes table shows next to the rollout.

Dataset scene provenance#

The goal is to rebuild a recorded episode’s scene from the dataset path and episode index alone. The rebuild has two halves: the scene config (robot, scene preset, table, cameras, lighting, physics) comes from code and flags, and the per-episode state (joints, gripper, block poses, table height) comes from the data through apply_setup. If the scene config does not match the one datagen used, the state lands on the wrong scene, so eval pins the scene to the dataset’s recorded provenance:

  • Datagen records scene_id and robot_id (per-step columns, or meta/info.json). generate_task_from_dataset.py bakes them into the generated env_cfg.py, and evaluate.py --dataset_path defaults the eval robot and scene preset to them (reconcile_env_cfg_with_dataset in utils/dataset_provenance.py).

  • A dataset that records neither, with no --robot-id / --scene-preset override, is rejected rather than run on a possibly wrong scene. An explicit override that disagrees is honoured with a warning; regenerating the task from the dataset (or dropping the override) is the usual fix.

  • The recorded block heights and table_height_delta are relative to the datagen preset’s table, so apply_setup restores the table from table_pose (absolute) or table_height_delta and fails rather than inferring it from block positions.

Validating dataset loading#

To confirm that the eval scene matches the dataset it was generated from:

  • scripts/eval/verify_dataset_loading.py (standalone, needs a GPU) applies each requested episode’s setup to a freshly reset environment, all in one Isaac session, and writes a scene diff (table height, blocks present, block and table poses, block sizes, camera intrinsics and pose), first-frame MAE / MSE / SSIM with side-by-side PNGs, and a check of the policy input built from the reset observation. It exits non-zero on any hard mismatch; each camera’s SSIM has a hard floor (--min-first-frame-ssim, default 0.90). Generate the task package first:

    python scripts/generate_task_from_dataset.py --dataset-path data/datasets/my_dataset --headless
python scripts/eval/verify_dataset_loading.py \
    --dataset-path data/datasets/my_dataset --task my_dataset-v0 --episode-indices 0 4 \
    --obs-mode rgb+state --output-dir runs/verify --headless --enable_cameras

  • evaluate.py --verify_scene runs the same scene checks on the first batch of queue setups during a live eval and writes scene_verification.json with comparison PNGs. Hard mismatches are only logged; --verify_scene_strict aborts the run after the report is written. Use strict whenever the numbers will be reported. These two flags are not exposed by launch_eval.py.

Evaluating on rerendered datasets#

The re-rendering stage gives every episode its own look:

  • its own camera offsets, HDRI sky, table material, lights, exposure and backdrop, recorded in meta/render_params.json (for a merged dataset, one file per source, reached through meta/provenance.json);

  • on glyph and colour rerenders, its own block letters and colours (block_variable_map / glyph_map).

By default, eval reproduces only the block identities. Everything else is the single calibrated sim2real scene. Four flags control how much of the recorded look is reproduced:

Flag

Default

Effect

--use-calibrated-cameras

on

Fixed sim2real camera intrinsics for every environment; also turns the render replay off. --no-use-calibrated-cameras gives each environment its episode’s recorded intrinsics instead.

--use-render-params

off

Reproduce each episode’s camera poses (and the wrist camera’s mount offset), HDRI sky, table material, lights, exposure and backdrop. Does nothing on datasets without render_params.json.

--wave-resets

off

Start episodes in waves, so all environments in a wave share one episode’s lighting (see the caveats below).

--replay-block-identity

on

Paint each episode’s recorded block letters and colours, and prompt the policy with the goal as rendered. Success is always graded on the source block names. --no-replay-block-identity keeps the original look and the source-name prompts.

To evaluate with the full recorded look:

python scripts/launch_eval.py --policy maniflow \
    --model-path data/checkpoints/my_maniflow_run/checkpoints/steps_400000_model.safetensors \
    --dataset-path data/datasets/my_rerendered_dataset \
    --no-use-calibrated-cameras --use-render-params --wave-resets

With --replay, drop --wave-resets, since replay runs a single environment per GPU.

What the launcher checks before it starts anything:

  • --use-render-params needs --no-use-calibrated-cameras.

  • --wave-resets needs --use-render-params and more than one environment, so it cannot be combined with --replay or with calibrated cameras.

Caveats:

  • Lighting is shared by the whole scene. The sky, lights and exposure are one setting for all environments. Without --wave-resets they are set once at the first reset, so with several environments most episodes run under another episode’s lighting.

  • Tiled rendering uses one set of intrinsics. Every environment is drawn with environment 0’s intrinsics, so an environment whose episode recorded different ones reports intrinsics that don’t match its pixels.

  • A mismatched record is skipped, not fatal. An episode whose render record fails the lookup checks (the episode count per source problem, the front camera position, the table height) runs with nothing applied, and the run carries on.

To check what was applied, look at each episode’s render_replay_status and block_identity_status (applied or none) in eval_episodes.json; see Metrics.

HL latency#

The four HL latency flags decouple the high-level conditioning (the oracle for --policy maniflow, the Molmo2 forward for --policy molmo2_maniflow) from per-step low-level inference, in milliseconds of sim time (sim_time_ms = step * step_dt * 1000; see src/toyblocks/serving/hl_latency.py). All default to 0, which runs the HL on every LL inference with no delay:

  • K (--hl-update-interval-ms): invoke the HL at most once per K ms and buffer its output in between. --hl-update-interval-jitter-ms j adds U(-j, +j) ms to each interval to mimic HL timing variance.

  • M (--estimated-hl-inference-time-ms): feed the LL the freshest HL output at least M ms old, faking the arm and physics advancing during HL inference.

The Molmo2 server only sees observations at action-chunk boundaries, so a K below action_horizon * step_dt is a no-op there; the client-side oracle buffer ticks every control step.

Checkpoints that read the previous front frame. A ManiFlow checkpoint trained with use_previous_front_frame also takes the aged HL frame as prev_front_rgb. There is no flag for it: the server advertises the input and the client sends it. M and K then have to match training: the dataloader pairs each frame with one n_action_steps * U{1,2,3,4} steps back (n_action_steps is in the checkpoint’s config.yaml), while the conditioning age cycles within [M, M + K]. So set M ≈ n_action_steps * step_dt * 1000 and size K so the age reaches about 4x that. Two settings print a loud startup warning naming the resulting age (neither is fatal, since each is also how a synchronous HL is configured on purpose):

  • M = 0: the conditioning frame is the current one at every chunk boundary.

  • K an integer multiple of the action-chunk period (action_horizon * step_dt * 1000): the HL commits phase-lock with the inferences, so the age is a constant M instead of sweeping [M, M + K). Offset K or add jitter to break the lock.

--save-diagnostic-plots writes hl_conditioning_staleness.png (client-side oracle HL only), the quickest check of what actually happened: K is the sawtooth period of the conditioning age and M its floor, and LL calls and HL commits are drawn as event lines. For the Molmo2 HL, the server-side HL input trace is the equivalent record.

Outputs#

Results go under RUNS_ROOT, which defaults to runs/ in the repository root (set RUNS_ROOT=/path in the environment of launch_eval.py to change it). Each eval worker N (seed N, from 1) writes to

runs/<task>-v0/<policy>/<out_subdir>/<problem_id>/seed_<N>/<YYYYmmdd_HHMMSS>_local/

with <policy> from --policy-name (maniflow, molmo2_maniflow or replay by default), <out_subdir> from the profile or --out-subdir, and <problem_id> from --problem-id. Besides the evaluate.py outputs (eval_results.json, eval_episodes.json, the LeRobot dataset, videos), each worker directory holds launch_params.json (the resolved launch parameters, including the commit), launch_command.sh (the command line), std_out_err.log (the pipeline log followed by that worker’s output) and skill_success.json (per-skill success rates from scripts/skill_success_from_eval_run.py).

At the end, scripts/merge_eval_runs.py merges the workers into one run directory, runs/<task>-v0/<policy>/<out_subdir>/<problem_id>/<run_id>/, with every worker’s episodes in one eval_episodes.json, the merged success LeRobot dataset (moved out of the workers; the failure datasets stay in them) and its own skill_success.json.

With --wandb, scripts/wandb_consolidate.py merges every worker into one W&B run named <policy>__<task>-v0__<out_subdir> (needs WANDB_API_KEY). It carries summary/run_stats_table (one row of headline numbers: success rates, episode lengths against the expert’s, timeout rate, throughput), eval/aggregates_table (every metric’s mean, std, min and max), videos/episodes_with_expert_table (one row per episode, with the expert video next to the rollout), and, under --save-diagnostic-plots, the debug/policy_inputs_table, debug/ll_policy_inputs_table and debug/hl_policy_inputs_table debugging tables.

Examples#

# Smoke test of Molmo2 high level + ManiFlow low level (the default policy)
python scripts/launch_eval.py --smoke-test \
    --model-path data/checkpoints/my_maniflow_run/checkpoints/steps_400000_model.safetensors \
    --hl-model-path data/checkpoints/my_molmo2_run \
    --dataset-path data/datasets/my_dataset

# ManiFlow with the high-level oracle, on 4 eval GPUs, logged to W&B
python scripts/launch_eval.py --policy maniflow --num-eval-gpus 4 \
    --model-path data/checkpoints/my_maniflow_run/checkpoints/steps_400000_model.safetensors \
    --dataset-path data/datasets/my_dataset --wandb

# Molmo2 high level + motion-planned skills (low-level oracle), episodes 0-19 only
python scripts/launch_eval.py --ll-oracle \
    --model-path data/checkpoints/my_maniflow_run/checkpoints/steps_400000_model.safetensors \
    --hl-model-path data/checkpoints/my_molmo2_run \
    --dataset-path data/datasets/my_dataset --episode-indices "0-19"

# Start after every flip or rotate, with a per-episode timeout of 1.5x the expert's
python scripts/launch_eval.py --policy maniflow \
    --model-path data/checkpoints/my_maniflow_run/checkpoints/steps_400000_model.safetensors \
    --dataset-path data/datasets/my_dataset \
    --init-after-hl-action flip,rotate --expert-timeout-scale 1.5

# Replay the dataset's recorded actions (no policy server; one cube scale)
python scripts/launch_eval.py --replay \
    --dataset-path data/datasets/my_dataset --episode-indices "0"

# Print the pipeline invocation instead of running it
python scripts/launch_eval.py --dry-run --policy maniflow \
    --model-path data/checkpoints/my_maniflow_run/checkpoints/steps_400000_model.safetensors \
    --dataset-path data/datasets/my_dataset --output /tmp/eval_run.sh

--async-hl

off

molmo2_maniflow with a play-mode LL: query Molmo2 only at episode start and when the LL ends a skill, instead of at every chunk boundary.

--async-hl-call-scale

no cap

With --async-hl: end an episode once Molmo2 has been called more than this multiple of its expert’s HL calls.

--ll-oracle

off

molmo2_maniflow: run Molmo2’s commands with the datagen motion-planned skills (cuRobo v2) instead of the served LL. Each command acts on the block nearest its pixel (or the table within 25 px), and Molmo2 is queried again per environment once it ends (implies asynchronous HL queries).

--ll-oracle-hl-call-scale

3.0

With --ll-oracle: the same HL call cap.

--go-home

off

With --async-hl or --ll-oracle: drive the arm home after a place, flip or rotate, before the next Molmo2 query.

on

On a glyph/colour-rerendered dataset, paint each episode’s recorded block letters and colours and prompt with the recorded goal. Success is graded on the source block names either way.

--wave-resets

off

Start episodes in waves, so each wave shares one episode’s recorded scene lighting. Needs a rerendered dataset and --num-envs > 1; not with --replay or calibrated cameras.

none

none
